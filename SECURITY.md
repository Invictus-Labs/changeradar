# Security policy

## Supported versions

ChangeRadar is a pre-1.0 release. Only the latest release (and the current `main`) receives security fixes. The supported-version policy for a 1.0 is an owner decision that has not been made yet.

## Reporting a vulnerability

Please do not open a public issue for a vulnerability. Use the repository's private vulnerability reporting (the "Security" tab, "Report a vulnerability"), if it is enabled. The maintainer has not yet published a dedicated security contact address; until one is published in this file, private reporting on the hosting platform is the channel. Include the version, what you did, what happened, and what you expected. You will get an acknowledgement as soon as the maintainer can give one; no response-time commitment is made by this pre-release.

## Security model in brief

ChangeRadar is a self-hosted daemon (API, worker and web UI) with a command line tool. What it protects and how:

- **No default credentials.** The first administrator is created locally with `changeradar admin create`; there is no default password and no open registration. Passwords are stored as salted scrypt hashes. Sessions are revocable, HttpOnly, SameSite=Strict cookies, with a CSRF token on every mutation and login rate limits.
- **Workspace isolation and roles.** Every query, worker job and download is scoped to the caller's workspace; another workspace's object ids answer 404, indistinguishable from unknown ids. Roles are viewer, operator and admin.
- **Local by default.** The server binds `127.0.0.1`. It makes no outbound request unless an administrator lists a host on the egress allowlist for read-only contract checks (GET or HEAD only; redirects and DNS answers are re-checked; loopback, private, link-local and metadata addresses are refused). There is no telemetry.
- **Secrets stay out (best effort).** Manifests hold credential aliases only; a manifest with a value in a recognised secret shape is rejected whole without echoing it, and reports, exports, views, bundles and logs are redacted with the same patterns. Detection is pattern based (`docs/MANIFEST.md` lists the shapes): a secret in a shape that is not listed is neither rejected nor redacted, so do not rely on it as a control. A password in a LISTED shape can still be partly shown: an unquoted value ends at a blank, a quote or a delimiter, so the part behind it stays readable (`password=z;o7:q3C|^<E` shows everything behind the `;`). Measured with a generator of random printable passwords in eight contexts, about 46 percent of such passwords (1,475,168 of 3.2 million cases, measured at 48fda4b; 46.8 percent by an independent measurement; 62.8 percent measured at 435731e, the round-4 build) leak part of their tail; this is a documented limit that the owner has not accepted, and it is not closed. Stored credential values are sealed with AES-256-GCM under an operator-managed key that lives outside the database. Logs never carry cookies, authorization headers, bodies or query strings; reports and exports are redacted.
- **Hostile input.** Size and structure limits (25 MB, 10,000 nodes, 50,000 edges) are enforced before processing; report text is HTML-escaped; the web UI and the static report run under a strict content security policy and never execute anything from a manifest.
- **Evidence bundles** are hash-verified on restore, and every finished run is re-derived from its recorded manifests and check results and compared field by field (every finding field, the unknowns, the assessment detail and the verdict), so corruption, accidental edits and edits to those derived fields are detected even when the hashes were recomputed. Fields outside that re-derivation (workspace name, snapshot revision and warnings, run events, timestamps (also the bundle's and the workspace's `created_at`, a snapshot's `imported_at` and the bundle's `baseline.version`), error text, `expected_hash`, `baseline_version`, `allow_superseded`, `check_keys`, `producer`, `scope`, contract check definitions, injected `PASSED` check rows) are covered by the hashes only, and a run from an older decision engine is not re-derived at all (it is marked re-run required). Export redacts the free text of a bundle (names, revisions, warnings, error and event text, unknowns, assessment detail, check definitions and results, contract check definitions); the manifests and the findings inside it are kept verbatim because the hashes and the re-derivation depend on them, and they were checked at import against the recognised secret shapes only (a plain-word credential such as `password=correcthorse` is not one, so it is stored and exported as written; views and reports redact it; see `docs/MANIFEST.md`, "Not covered"). This is integrity, not authenticity: bundles are not signed with an operator key, so someone who rewrites the recorded inputs together with everything derived from them and recomputes every hash produces a bundle that cannot be told from a real one (tests pin both limits). Restore never re-arms anything from a bundle: contract checks come back disabled and free text is bounded. Treat a bundle from an untrusted source as untrusted input.
- **Terminal output** of every CLI command is escaped: control, escape, bidirectional and separator characters from a file or an argument are shown as `\u{...}`, never sent raw to the terminal.
- **Outbound requests.** Besides read-only contract checks (GET or HEAD only), an operator may configure an event sink (`CHANGERADAR_EVENT_SINK_URL`): the server then POSTs the versioned event envelope (ids and references, no manifest content) to that one allowlisted URL, under the same egress rules. With neither configured nothing leaves the machine. A stored credential is sent only to the origin its check was configured for, never after a redirect to another origin.
- **Sessions and members.** Sessions are revocable: logout ends one, and `changeradar admin revoke --email E --workspace-id ID [--remove-member]` ends every session of a member; the membership is removed only with `--remove-member`, otherwise the member can sign in again. Sessions are checked on every request.
- **The embedded database** belongs to one process at a time; a second opener is refused.

## Known limits

Plain HTTP only (put a TLS reverse proxy in front for anything beyond localhost; rate limiting keys on the socket address until a trusted-proxy setting exists, so behind a proxy one client can use up the per-address budget of everyone behind it; limit per client at the proxy). One embedded-database process at a time. Retention is reported, never applied automatically, and its defaults need operator approval before real data is ingested. Sealed credentials carry no associated data (a party with write access to the database could move a sealed value between aliases or workspaces), one key serves both encryption and the keyed hash without a key derivation step, and the password hash uses scrypt N = 2^14: changing any of them changes the stored format, which needs a migration, so they are recorded here as accepted limits for this pre-release. Building and verifying one bundle at the largest supported size occupies the server's single thread for about three seconds; it is bounded by the bundle budget (4 per window per user), at most two exports at once and the size cap, not removed. Independent security review has not been done for this pre-release.
