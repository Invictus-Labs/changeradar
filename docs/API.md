# ChangeRadar HTTP API (v1)

Base path `/api/v1`. All bodies are JSON (`content-type: application/json`; any other request body type is rejected with 400). All timestamps are UTC ISO 8601 with a trailing `Z`. All ids are UUIDs except content-derived ids (`fnd_`, `chg_`, `unk_`, `cyc_`, `sha256:`), which are text. Request bodies have machine readable JSON Schemas generated from the server's own validators: `schemas/api-requests.json` (snapshot import, impact run request, contract check) and `schemas/dependencies.json` (the manifest); tests fail if either drifts. **Response bodies have machine readable JSON Schemas too**: `schemas/api-responses.json` (draft 2020-12) covers the error envelope, health, login and session, the snapshot receipt, summary and list, the impact run receipt, view and list, the findings page and the JSON run report. They are written once as zod schemas (`src/domain/api-responses.ts`), generated into the file (`npm run schema:generate`, drift is a test and `npm run schema:check` failure), and validated against REAL responses of a running server in every documented state by the contract tests (`tests/integration/review-round2-contract.test.ts`). Members not listed in a schema are drift: the top level objects are closed. Behavior described here is covered by the tests named in `docs/qa/ac-matrix.md`.

This document is the contract for the UI and report stage. Domain semantics (verdicts, unknowns, ids) are defined in `docs/DOMAIN.md`; the manifest format in `docs/MANIFEST.md`.

## Conventions

| Topic | Rule |
| --- | --- |
| Errors | `{"error":{"code","message","request_id"}}` plus, for some 409/422 responses, `error.details` (structured, never contains submitted values). `request_id` equals the `x-request-id` response header. |
| Status codes | 400 malformed input, 401 unauthenticated, 403 forbidden action, 404 inaccessible object (also unknown routes), 409 version or idempotency conflict, 413 oversize payload, 422 schema or policy rejection, 429 rate limit, 503 dependency unavailable. 500 is used only for bugs and integrity failures and is always generic. |
| Pagination | List endpoints return `{items, next_cursor}`. `?limit=` is 1 to 100 (default 50, anything else is 400 `INVALID_LIMIT`). `next_cursor` is opaque; pass it back as `?cursor=`. A malformed cursor is 400 `INVALID_CURSOR`: the wrong shape, a position that is not a non-negative integer that fits its column, a timestamp that is not a real UTC instant (`2026-02-31T00:00:00Z`, a bare year, an expanded or negative year), a value that is not a UUID. A value the database itself refuses (SQLSTATE class 22) is a 400 as well, never a 500. |
| Run status | Lower case: `queued`, `running`, `complete`, `failed` (the same spelling as the `202` receipt). `complete` describes computation, not safety. The verdict is the separate `assessment` field: `AFFECTED`, `NO_KNOWN_IMPACT` or `INCOMPLETE` (null until complete, and null for a finished run assessed by an older decision engine: its old verdict is `recorded_assessment`, next to `engine.rerun_required`). |
| Idempotency | Send `Idempotency-Key` (1 to 128 characters of `A-Za-z0-9._:-`) on `POST /snapshots`, `POST /impact-runs`, `POST /contract-checks`. Scope is workspace + actor + route. Same key and byte-identical body returns the stored receipt (`idempotent-replayed: true` header, same status); same key with a different body is 409 `IDEMPOTENCY_CONFLICT`. Replays are answered before any state-dependent validation, so a lost-response retry of an accepted request returns the original receipt even if the baseline has since moved. Failed requests store nothing. Keys are retained at least 7 days. |
| Cookies and CSRF | Session cookie `changeradar_session` (HttpOnly, SameSite=Strict, Path=/, Secure unless the public URL is plain http). Every non-GET request must carry `x-csrf-token` equal to the value returned by login or `GET /auth/session`. |
| Security headers | Every response: `x-content-type-options: nosniff`, `x-frame-options: DENY`, `referrer-policy: no-referrer`, `cache-control: no-store`, a CSP (`default-src 'none'; frame-ancestors 'none'`, relaxed only for the HTML export), `x-request-id`. No CORS headers are ever sent (same origin only). |
| Limits | Manifest 25 MB (`413 PAYLOAD_TOO_LARGE`), 10,000 nodes (`413 TOO_MANY_NODES`), 50,000 edges (`413 TOO_MANY_EDGES`), enforced before any item is validated. Request body = manifest limit + 64 KiB envelope on `POST /snapshots` and `POST /impact-runs`; 64 KiB on every other route. Evidence bundle 64 MiB by default (`CHANGERADAR_MAX_BUNDLE_BYTES`; memory is about 40 times the bundle size for ordinary text and up to about 130 times for a bundle made of numbers or one-key objects (measured), see `docs/OPERATIONS.md`), enforced by export, `verify-bundle` and `restore` alike (`BUNDLE_TOO_LARGE`). Rate limits: logins per account and per address, and authenticated calls per user, per minute (`429 RATE_LIMITED` with `retry-after`). |

## Roles

`viewer` reads redacted reports and graphs. `operator` also imports snapshots, requests runs, downloads manifests and evidence bundles, reads contract-check definitions and events. `admin` also manages contract checks, members, audit, settings. Every service function checks the role itself (defense in depth), and the tests assert a matrix of 21 cases (20 distinct routes, `export` counted for both formats) by 3 roles and fail when a route is added without a row.

| Route | viewer | operator | admin |
| --- | --- | --- | --- |
| `GET /baseline`, `GET /snapshots`, `GET /snapshots/{id}`, `.../nodes`, `.../edges` | yes | yes | yes |
| `POST /snapshots`, `GET /snapshots/{id}/manifest` | no | yes | yes |
| `GET /impact-runs`, `GET /impact-runs/{id}`, `.../findings`, `.../export` | yes | yes | yes |
| `POST /impact-runs`, `GET /impact-runs/{id}/bundle` | no | yes | yes |
| `GET /contract-checks`, `GET /events` | no | yes | yes |
| `POST /contract-checks`, `POST /contract-checks/{id}/disable`, `GET /members`, `GET /audit`, `GET /settings` | no | no | yes |

## Health

`GET /health/live` -> 200 `{"status":"ok","version"}` always. `GET /health/ready` -> 200 `{"status":"ready","version"}`, or 503 `NOT_READY` when migrations failed, the schema is behind this build, or the database is unreachable. While not ready every other route also answers 503 `NOT_READY`.

## Authentication

- `POST /auth/login` `{email, password, workspace_id?}` -> 200 `{user:{id,email,workspace_id,workspace_name,role}, csrf_token}` and `Set-Cookie`. Wrong password and unknown account are indistinguishable (401 `INVALID_CREDENTIALS`). The session is bound to one workspace (the first by name when `workspace_id` is omitted).
- `GET /auth/session` -> 200 `{user, csrf_token}`. `POST /auth/logout` -> 200 `{ok:true}` and revokes the session server side.
- There is no registration and no default password. Users are created with `changeradar admin create` (see `docs/OPERATIONS.md`).

## Snapshots and the baseline

A snapshot is an immutable, content-hashed import of a manifest. The workspace has a **baseline**: the most recently imported snapshot. Impact runs are assessed against the baseline; if it moves while a client is working from an older snapshot, the request is refused (409) rather than assessed against a stale view.

- `POST /snapshots` `{schema_version:1, revision, manifest}` -> **201** `{id, hash, warnings, revision, document_hash, schema_version, node_count, edge_count, baseline_version, is_baseline:true, imported_at}` and `Location`. `hash` is the graph hash to use as `expected_hash`. `warnings` is the domain's aggregated warning list (cycles, missing owners, placeholders, unverified edges). Validation (size, counts, schema version, structure, secrets, references) completes before anything is written; a rejection leaves no row anywhere. 422 responses carry `error.details.issues` (JSON pointer, code, message; never the submitted value) and `total_issues`.
- `GET /baseline` -> `{snapshot: <summary>|null, baseline_version}`.
- `GET /snapshots` (newest first), `GET /snapshots/{id}` -> summary `{id, revision, hash, document_hash, schema_version, node_count, edge_count, baseline_version, is_baseline, imported_at, warnings}`.
- `GET /snapshots/{id}/nodes` (by id), `GET /snapshots/{id}/edges` (by source, target, relation) -> the stored graph rows.
- `GET /snapshots/{id}/manifest` (operator+) -> the normalized manifest; rebuilding it reproduces `hash`. A stored manifest that the current validator no longer accepts (an earlier build stored it before a secret shape was recognised) is served redacted, with the header `x-changeradar-manifest-redacted` holding the stored document's hash; the stored row is not rewritten. The stored manifest is validated again on every download (about 330 to 450 ms for a 9,000-node manifest, against 20 to 35 ms without it), so a legacy manifest is redacted whenever the validator has learned a new shape; downloads are audited and share the export budget.

## Impact runs

`POST /impact-runs` `{snapshot_id, proposed_manifest, expected_hash, run_checks?=true, check_keys?, allow_superseded?=false}` -> **202** `{id, status:"queued", snapshot_id, baseline_hash, proposed_hash, baseline_version}` and `Location`.

Order of decisions (cheapest first, nothing persisted until the last step): role; body shape (422 `SCHEMA_INVALID`); the snapshot must be in your workspace (404, so a foreign id changes nothing and reveals nothing, even with the right hash); `expected_hash` against the snapshot hash (422 `INVALID_EXPECTED_HASH` if malformed, 409 `STALE_BASELINE` if different); proposed manifest limits and validity (413/422); `check_keys` must name enabled checks (422 `UNKNOWN_CHECK`, whose `details` carry only a count and the positions in your list, never the submitted keys); then one transaction that locks the workspace row and returns 409 `STALE_BASELINE` (with `details.current_baseline_snapshot_id` and `baseline_version`) when the snapshot is no longer the baseline. With `allow_superseded: true` a superseded snapshot is accepted (still hash-checked) and the run records `allow_superseded: true`.

`run_checks` (default true) runs the enabled contract checks whose `node_id` is among the changed nodes, or exactly `check_keys` when given (at most 50 per run, otherwise the run ends `failed` `TOO_MANY_CHECKS`).

`GET /impact-runs` items carry `rerun_required` (true for a finished run assessed by an older engine). For such a run `assessment` is `null` in the list, in `GET /impact-runs/{id}` and in the JSON export, and `recorded_assessment` holds the verdict the older engine recorded (it is `null` for every run of the current engine and for an unfinished run), so a client that gates on `assessment == "NO_KNOWN_IMPACT"` cannot accept a run whose rules are out of date. The UI shows "Re-run required" and the HTML export a "RE-RUN REQUIRED" block with every count and list labelled as the older engine's.

**The consumer rule: how to read a run's verdict.** Only `assessment == "NO_KNOWN_IMPACT"` on a run of the current engine (`engine.rerun_required` false, `recorded_assessment` null) means "no declared consumer is affected". Everything else is NOT safe: `null`, `INCOMPLETE` and `AFFECTED` all mean "do not proceed on this run alone". `null` with `status: "complete"` means a re-run is required (the run is finished, it is never pending); `null` with `queued`, `running` or `failed` means there is no verdict yet. One function decides which runs are stale (`isStaleEngineRun` in `src/services/assess.ts`), and every surface below follows it:

| Surface that prints or exports a run's verdict | Behaviour for a run of an older engine | Test |
|---|---|---|
| `GET /impact-runs/{id}`, `GET /impact-runs` | `assessment` null, `recorded_assessment` set | `tests/integration/review-round4-stale.test.ts` (response schemas parsed at the HTTP layer) |
| JSON export | same fields | same file |
| HTML export | "RE-RUN REQUIRED" block, every count and list labelled as the older engine's | same file |
| Web run view, run list, empty findings text | banner and cell say "re-run required" | `tests/web/states.test.tsx` |
| Evidence bundle (`GET /impact-runs/{id}/bundle`, `changeradar export`) | the bundle's field for the verdict is `impact_runs[].verdict` (the API's `assessment` is the same value for a current run) and it keeps the RECORDED verdict for a stale run, as hashed evidence; the stale runs are named in the top-level `stale_runs` member (outside every hash, checked against the runs), by the response header `x-changeradar-stale-runs` (the count, 0 for a current run) and by the CLI export message; `verify-bundle` and `restore` list them | `tests/integration/review-round5-stale-bundle.test.ts`, `tests/integration/review-round3-evidence.test.ts`, `tests/integration/review-round4-evidence.test.ts`, `tests/integration/review-round3-cli.test.ts` |
| `summary`, `affected`, `paths`, `totals` of the run view, the JSON export's `findings`, and `GET /impact-runs/{id}/findings` | the older engine's recorded record, unchanged and unmarked in themselves: a stale run whose old verdict was NO_KNOWN_IMPACT has `summary.known_impact` false, no findings and an empty findings page. They are history: read `engine.rerun_required` (or `assessment` being null) of the same run first (the findings page also carries `rerun_required`, true for such a run), never `summary.known_impact` or an empty findings list on their own | `tests/integration/review-round4-stale.test.ts` |

| Run events, audit rows, outbox | the outbox envelope carries no verdict; an event note or audit metadata states the verdict at the time it was written and is history, not a current answer | `tests/integration/review-round4-audit.test.ts` |

There is no filter or sort on the verdict. The list endpoint filters by `status` and `snapshot_id` only.

**Recorded deviation: the run view is not paged.** The product requirements say lists cap at 100 entries with cursor pagination. `GET /impact-runs/{id}` returns its `changes` (at most 10,000, with `CHANGES_LIST_TRUNCATED` beyond that) and its `cycles` in the one response, unpaged, because the run view, the JSON export and the HTML report must show the same complete list and a change list cut at 100 would make the three disagree; the totals are in `summary`. Findings, unknowns-heavy runs and every collection list ARE paged (`/findings`, snapshots, nodes, edges, runs, events, members, checks). The size of the run view is bounded by the limits above. This deviation is recorded here and in the acceptance matrix and needs the product owner's decision; none is granted.

`GET /impact-runs/{id}` -> 200 (`engine` says which decision engine assessed the run: for a finished run assessed by an older engine, `rerun_required` is true and `note` says "assessed by an older decision engine ... re-run required"; the same member is in the JSON report's `run` and printed in the HTML report; runs stored before the stamp existed are version 1)

```json
{
  "id": "...", "snapshot_id": "...", "status": "complete", "assessment": "AFFECTED", "recorded_assessment": null,
  "baseline_hash": "sha256:...", "proposed_hash": "sha256:...", "baseline_version": 3, "allow_superseded": false,
  "created_at": "...", "started_at": "...", "finished_at": "...", "error": null,

  "summary": {"changes": 1, "findings": 3, "direct_findings": 1, "transitive_findings": 2, "unknowns": 0, "known_impact": true},

  "unknowns": [{"id": "unk_...", "code": "STALE_CONTRACT", "node_id": null, "edge": {"source_id": "...", "target_id": "...", "relation": "consumes"}, "message": "..."}],
  "checks": [{"check_key": "...", "node_id": "...", "state": "PASSED", "attempts": 1, "detail": "...", "error_code": null, "attempt_log": [{"attempt": 1, "state": "PASSED", "detail": "...", "error_code": null}], "started_at": "...", "finished_at": "..."}],
  "totals": {"findings": 3, "unknowns": 0},
  "truncated": {"findings": false, "unknowns": false}

```

**Bounded output.** A valid manifest can imply a quadratic number of (changed node, consumer) pairs, so the assessment is bounded: at most 5,000 findings per run and 1,000 per changed node (closest consumers first), 16 MB of findings, 2,000 unknowns, 10,000 listed changes (all changes are evaluated; changes that can affect consumers are listed first), and a traversal budget of two million dependent links. A finding whose path is longer than 24 hops keeps its first 12 and last 12 hops and says so with `path_omitted_hops` (`path` is the origin followed by the `to` of every kept hop; `hops.length === depth` only when nothing was omitted), and a finding caused by more than 20 changes lists 20 ids and says how many are left in `change_ids_omitted` (the `reason` quotes three descriptions and counts the rest). Both fields are absent when nothing was left out. Reaching any limit adds the unknown `FINDINGS_TRUNCATED` (or `UNKNOWNS_TRUNCATED`) and the coverage limit of the same name, so the run is INCOMPLETE, never a safe verdict; `summary.findings_omitted` and `summary.changes_omitted` give the counts. A run whose whole assessment would still exceed 40 MB fails with `OUTPUT_TOO_LARGE` and stores nothing.

`affected` and `paths` carry the first 100 findings, `unknowns` the first 100; `totals` gives the full counts and `truncated` says whether to page `GET /impact-runs/{id}/findings` (`{items:[finding with path and hops], next_cursor}`, ordered as the assessment ordered them). While `queued` or `running`, `assessment` is null and `affected`, `paths`, `unknowns` are empty. A `failed` run has `error: {code, detail}` and no verdict: `WORKER_EXHAUSTED` (the job kept failing or crashing), `INTEGRITY_FAILURE` (stored data no longer matches its recorded hash), `TOO_MANY_CHECKS`, `RESTORED_UNFINISHED` (restored from a backup while unfinished).

Check states: `STARTED` (in flight), `PASSED`, `FAILED` (the endpoint answered wrongly), `TIMED_OUT`, `ERROR` (transport failure, policy refusal, missing credential), `UNKNOWN` (interrupted by a worker restart: the outcome cannot be known and the check is not re-run). Anything other than `PASSED` becomes an unknown and forces `INCOMPLETE`.

`GET /impact-runs?status=&snapshot_id=&limit=&cursor=` -> `{items:[{id, snapshot_id, status, assessment, recorded_assessment, proposed_hash, created_at, finished_at, rerun_required}], next_cursor}` newest first.

## Exports

- `GET /impact-runs/{id}/export?format=json` (default) -> the **run report**: `{schema_version:1, format:"changeradar-run-report", run, snapshot, summary, coverage, cycles, changes, findings:[...all], unknowns:[...all], checks, report_hash}`. Redacted, deterministic for a finished run (no generation timestamp); `report_hash` is the sha256 of the canonical JSON of every other member. Finding ids (`findings[].id`) are the same content-derived ids the API shows and the HTML shows.
- `GET /impact-runs/{id}/export?format=html` -> a complete standalone HTML document (`text/html`, CSP `default-src 'none'; style-src 'unsafe-inline'`).
- `GET /impact-runs/{id}/bundle` (operator+) -> the evidence bundle of this run and its baseline snapshot (see below), `content-disposition: attachment`.

**HTML renderer contract** (implemented in `src/report/html-report.ts`, the self-contained static report): `interface ReportRenderer { render(report: RunReport): string }` in `src/services/report.ts`. It receives exactly the object the JSON export serves, must return one complete document, must escape every dynamic value (`escapeHtml`, `safeReportText` in `src/domain/redaction.ts`), and must print every `findings[].id` verbatim. Register it on the context (`ctx.reportRenderer`); until one is registered a safe built-in renderer (`defaultReportRenderer`) is used. Tests prove the JSON export and the HTML export list identical ids and that a registered renderer receives the same object.

## Evidence bundle (backup, restore)

A single JSON document (canonical encoding, trailing newline): `{format:"changeradar-evidence-bundle", schema_version:1, scope:"workspace"|"run", created_at, producer, workspace:{id,name,created_at}, baseline, snapshots[], impact_runs[], contract_checks[], hashes:{snapshots,impact_runs,contract_checks}, bundle_hash, stale_runs?}` (`stale_runs`, present only when a run from an older engine is inside, lists their ids and is outside every hash). Snapshots carry their normalized manifest; runs carry the proposed manifest, assessment detail, all findings, check results and run history. It contains no users, sessions, password hashes, credential values or idempotency keys, and the free text is redacted at export: workspace name, snapshot revision and warnings, run error code and detail, check keys, unknowns, assessment detail, event notes, check definitions and results, and the contract check definitions. Manifests and findings are kept verbatim (the hashes and the re-derivation depend on them; they were vetted at import).

Verification before anything is written (`changeradar verify-bundle`, `changeradar restore`): size cap; valid UTF-8 JSON with no repeated object key (`BUNDLE_MALFORMED`, which is also what a truncated file reports; `BUNDLE_DUPLICATE_KEY`); `schema_version` supported (else `BUNDLE_UNSUPPORTED_VERSION`); strict shape (`BUNDLE_SCHEMA_INVALID`, which is also the code for an object key longer than 2,000 characters, an object key of six characters or more whose REDACTED form is longer than 2,000 characters (redaction can lengthen a key: `pwd: a|` repeated grows about 2.1 times, so a key of 994 characters can be refused, and the refusal says "once redacted"), and for an unpaired surrogate anywhere in the bundle, at `verify-bundle` and at `restore`); bundle hash and section hashes (`BUNDLE_HASH_MISMATCH`, an edited file); every snapshot rebuilt and re-hashed (`BUNDLE_SNAPSHOT_MISMATCH`); every finished run re-derived with the pure assessor at its recorded evaluation time and compared field by field: every finding field, the unknowns, the assessment detail and the verdict must reproduce (`BUNDLE_RUN_INCONSISTENT`, which catches an edit to any of those even when the hashes were recomputed, and refuses a recorded text longer than 8,000 characters without redacting it: no engine derives one, and a text of that size is hostile input; texts are compared after a cut to the 2,000-character bound, so a run written by an earlier build, whose derived message was cut at another character, still verifies), for a run assessed by THIS build's decision engine. A run from a NEWER engine, or with an engine version that is not a whole number, is refused with `BUNDLE_ENGINE_VERSION`. A run from an OLDER engine (a missing stamp means version 1) is not re-derived, because the old rules are not in this build: it is accepted on the hashes alone and reported as stale (`verify-bundle` and `restore` print the ids; restore returns `stale_runs`), so an upgrade never makes a workspace impossible to export; it is marked re-run required everywhere it is shown. Finding positions must be 0, 1, 2, ... Not re-derived, covered by the hashes alone: workspace name, snapshot revision and warnings, run events, timestamps (also the bundle's and the workspace's `created_at` and a snapshot's `imported_at`), error text, `expected_hash`, `baseline_version`, `allow_superseded`, `producer`, `scope`, the bundle's `baseline.version`, injected check rows and contract check definitions. `changeradar export` and `GET /impact-runs/{id}/bundle` verify the bundle they just built with the same code and fail (nothing is written or served) rather than produce one that could not be restored: 409 with the `BUNDLE_*` code, or 413 `BUNDLE_TOO_LARGE` when the bundle is over the installation's limit (default 64 MiB, `CHANGERADAR_MAX_BUNDLE_BYTES`). Bundle downloads have their own budget (4 per window per user, 12 for all exports) and at most 2 exports are built at once. Contract checks are restored disabled. A bundle that fails any step is refused whole. Restore writes in one transaction into a clean installation (an existing workspace, snapshot or run id is refused) and preserves all ids. **Integrity, not authenticity:** the hashes and the re-derivation detect corruption, accidental edits and edits to derived fields; nothing is keyed to the operator, so a forger who rewrites the recorded inputs (for example a check result) together with everything derived from them and recomputes every hash produces a bundle that cannot be told from a real one (a test pins this limit).

## Contract checks (admin configured, read-only)

- `POST /contract-checks` `{key, node_id, url, method?="GET"|"HEAD", timeout_ms?, retries?=2 (0 to 3), expect_status?=200, required_fields?:[{name, type}], credential_alias?}` -> 201 (the definition plus `credential_configured`). `url` must be on the operator egress allowlist (422 `URL_NOT_ALLOWED` with `details.reason`), with no credentials or secrets in it (422). `key` is unique per workspace (409 `CHECK_EXISTS` while the check is enabled). A DISABLED check with the same key (disabled by an administrator, or restored from a bundle, which never re-arms a check) is replaced by the definition posted, after the allowlist and secret rules have run: same id, enabled again, audit action `contract_check.reenabled`, 201. `required_fields` names and `credential_alias` are scanned for secret shapes like every other identifier (422 `SECRET_VALUE_REJECTED`, never echoed).
- `GET /contract-checks` (operator+; `{items, next_cursor}` ordered by key), `POST /contract-checks/{id}/disable` (admin, idempotent).
- The credential VALUE never passes through the API. `credential_alias` is only a name; the value is stored sealed (AES-256-GCM, operator-managed key) by `changeradar credential set` and sent only as `Authorization: Bearer ...`, dropped on cross-origin redirects.
- Runtime rules: GET or HEAD only; every hop including redirects checked against the allowlist; DNS answers all classified and the connection pinned to the vetted address; loopback, private, link-local and metadata addresses refused (a test-only setting relaxes loopback and private, never link-local or metadata); per-attempt timeout (`timeout_ms`, at most the operator maximum), response body cap, at most three retries with exponential backoff for `ERROR` and `TIMED_OUT` only; failures are visible and never converted to passed.

## Operations endpoints

- `GET /events?limit=&cursor=` (operator+) -> `{items:[{seq, state:"pending"|"delivered", envelope}], next_cursor}` where `envelope` is the PRD adapter envelope `{schema_version:1, event_id, source:"changeradar", resource_id, event_type, occurred_at, revision, evidence_ref}` (`event_type`: `snapshot.imported`, `impact_run.completed`, `impact_run.failed`). Events are written in the same transaction as the change they announce. Delivery is at least once: consumers deduplicate on `event_id`; a reader that must not miss a late-committing transaction re-reads from slightly before its cursor. Optional push delivery to `CHANGERADAR_EVENT_SINK_URL` is off by default and follows the egress rules.
- The free-text members of an event envelope (`revision`, `evidence_ref`, `correlation_id`) are redacted with the log redactor when the envelope is written and again whenever it is served by `GET /events` or handed to the event sink, so a row written by an earlier build is never shown as stored; audit metadata is redacted again when served in the same way.
- `GET /audit` (admin) -> append-only audit records (redacted metadata). Recorded: snapshot imports, run requests and completions, contract check creation, re-enabling and disabling, restores, retention, member changes, and (round 4) logins and logouts (`auth.login`, `auth.logout`), manifest downloads (`snapshot.manifest_downloaded`), run exports (`impact_run.exported`, with the format) and bundle downloads (`impact_run.bundle_downloaded`). Only a successful answer is recorded; a row holds who, what and which resource, never content or an address. A failed login is not a row (it is a rate-limited, logged event).
- `GET /members` (admin) -> `{items:[{user_id,email,role}], next_cursor}` ordered by email.
- `GET /settings` (admin) -> effective limits, rate limits, egress policy summary, and the proposed retention defaults with `retention.enforced: false`.

## Error codes

| Status | Codes |
| --- | --- |
| 400 | `MALFORMED_JSON`, `DUPLICATE_JSON_KEY` (an object key repeated anywhere in the body), `JSON_TOO_COMPLEX` (nesting over 64 levels or a container bomb), `BAD_REQUEST` (for example a non-JSON body), `INVALID_COOKIE`, `INVALID_REQUEST`, `INVALID_LIMIT`, `INVALID_QUERY`, `INVALID_CURSOR`, `INVALID_FORMAT`, `INVALID_IDEMPOTENCY_KEY` |
| 401 | `UNAUTHENTICATED`, `INVALID_CREDENTIALS` |
| 403 | `FORBIDDEN`, `CSRF_INVALID` |
| 404 | `NOT_FOUND` |
| 409 | `STALE_BASELINE`, `IDEMPOTENCY_CONFLICT`, `CHECK_EXISTS` (an ENABLED check with that key; a disabled one is replaced and re-enabled by the same POST), a `BUNDLE_*` code when a stored run cannot be exported (`INVALID_RUN_TRANSITION` is a domain error of the run state machine; no HTTP route can return it) |
| 413 | `PAYLOAD_TOO_LARGE`, `TOO_MANY_NODES`, `TOO_MANY_EDGES`, `BUNDLE_TOO_LARGE` |
| 422 | `SCHEMA_INVALID`, `UNSUPPORTED_SCHEMA_VERSION`, `SECRET_VALUE_REJECTED`, `DUPLICATE_NODE_ID`, `DUPLICATE_EDGE`, `DUPLICATE_CONTRACT_FIELD`, `DANGLING_EDGE`, `CONTRACT_ON_NON_CONTRACT_NODE`, `EDGE_FIELDS_ON_NON_CONTRACT_TARGET`, `INVALID_EXPECTED_HASH`, `UNKNOWN_CHECK`, `URL_NOT_ALLOWED` |
| 429 | `RATE_LIMITED` (also on exports and bundles: 12 exports and 4 bundle downloads per window per user, 2 built at once; the per-address limiters key an IPv6 client by its /64; `Retry-After` says when to retry) |
| 500 | `INTERNAL`, `INTEGRITY_FAILURE` (generic messages only) |
| 503 | `NOT_READY` (startup, a failed migration, and a database that became unreachable after startup: every route, with `Retry-After`) |
