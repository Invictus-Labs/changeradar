# Acceptance criteria matrix (consolidated: domain library, API and persistence, UI, packaging and end to end)

Source of truth for the criteria: `docs/prd/changeradar.md` section 5 (AC-01 to AC-13), section 5b (test strategy) and section 5c (definition of done).

This matrix covers the whole build: the **domain library** (stage A: pure code in `src/domain` and `src/services`), the **backend** (stage B: HTTP API, persistence, job worker, network contract checks, evidence bundles, CLI), the **web UI and static report** (stage C-1) and **packaging, acceptance suite, end-to-end runs and the operator documents** (stage C-2). It is an implementer's record: it is **not** an independent review or QA receipt, and no row is claimed PASS beyond what is listed with a named test that ran and passed. Commands, exit codes, UTC times, counts and coverage for the tested revision are in `docs/qa/stage-c2-evidence.md`; earlier stage records are `docs/qa/stage-b-evidence.md` and `docs/qa/ui-evidence.md`.

**Provisional, on purpose.** `docs/qa/stage-c2-evidence.md` records the gate of an EARLIER revision (the round-1 tested revision) and is marked superseded. The full local gate at the final revision of the remediation (after the seventh review round and its remediation) is **pending**, and so is a full run of every mutation harness (a gate step, not executed): every KILLED recorded in this matrix, in the evidence files and in the ledger is a targeted run at the revision that record names, not a claim about the final revision: until its receipt is recorded, every PASS below is provisional and means "proven by the named tests as run by the implementer during remediation", not "gated at the final SHA". The finding-by-finding record of the seven review rounds is `docs/qa/review-round1-ledger.md`. The named tests added in rounds 2 to 7 are listed per criterion in "Regression evidence added in review rounds 2 to 7" below.

**Recorded deviation from the product requirements** (needs the product owner's explicit waiver; none is granted here): finding ids are content-derived text (`fnd_` plus 20 hex characters), not UUIDs, because AC-03 and AC-07 need the same id in every export. (Request AND response JSON Schemas ship in `schemas/`; the response schemas are checked against real server responses by `review-round2-contract.test.ts`, so there is no schema deviation.)

**Recorded deviation (open, product owner to decide): the run view is not paged.** The product requirements say lists cap at 100 entries with a cursor. `GET /impact-runs/{id}` returns all of its `changes` (at most 10,000) and its `cycles` in one response, unpaged; findings and every collection list are paged. It is pinned by `review-round4-runview.test.ts` (130 changes in one view) and described in `docs/API.md`. It is not waived.

**Recorded deviation (open, product owner to decide): the default bundle cap is 64 MiB, not 250 MB.** The product requirements (section 5) name 250 MB. A bundle is verified and restored in memory at about 40 times its size for ordinary text and up to about 130 times for one made of numbers or one-key objects, so 64 MiB is what a 4 GB installation restores for ordinary text (a bundle of numbers can need several GB); `CHANGERADAR_MAX_BUNDLE_BYTES` raises it for a host that can. A run bundle stays far below it. `docs/API.md`, `docs/OPERATIONS.md`, `.env.example` and the tests say 64 MiB; the requirement text is an owner amendment item and is not changed here. It is not waived.

**An id that ends at a describe title** (for example `states.test.tsx :: empty states`) names every test of that block; `tests/unit/ac-matrix-ids.test.ts` checks that every id in this file names a test file and titles that exist (a wildcard or a placeholder is refused).

## Status vocabulary

- **PASS (domain)**: the named test is in `tests/unit/` and passed in the full server suite at the tested revision (`docs/qa/stage-c2-evidence.md`).
- **PASS (server)**: the named test is in `tests/integration/` (or `tests/unit/ssrf.test.ts`, `tests/unit/platform.test.ts`) and passed in BOTH database runs: the embedded engine and a real PostgreSQL 17 server. Network checks ran against a local FIXTURE HTTP server (a real socket and real HTTP path, never a mock of the runner, and never presented as a live provider).
- **PASS (spec)**: the named test is in `tests/changeradar.spec.ts`, the acceptance suite indexed by the PRD section 5b flows (real HTTP API, real persistence, real worker, fixed UTC clock). It runs in both database runs.
- **PASS (web)**: the named test is in `tests/web/` (jsdom render tests; API-backed ones talk to the real server, embedded database and worker, no route mocks; mocked fetch only for states a real server cannot be made to produce).
- **PASS (browser)**: the named test is in `tests/e2e/smoke.spec.ts`: real Chromium against the real compiled server, real embedded database and real worker; console, exception, dialog and network invariants asserted in every test.
- **PASS (packaged)**: the named test is in `tests/e2e/packaged.spec.ts`: the `npm pack` tarball installed in a fresh directory outside the repository and driven through its own binary.
- **PASS (compose)**: `scripts/compose-smoke.mjs`, a real `docker compose up --build` with PostgreSQL 17, throwaway project, loopback-only port, torn down afterwards.
- **PENDING_HUMAN_RECEIPT**: requires a receipt from an independent human (AC-11). The maintainers build the runbook and the automated fresh-directory harness; any automated drill is supplemental evidence only. Never PASS and never satisfied until a human receipt exists; no acceptance waiver is authorized.
- **PASS (implementer)** as an overall status means every part of the criterion is proven by the named tests at the tested revision. It is not an independent receipt: independent code review and QA at the final revision are still required and are not claimed here.
- **PARTIAL**, **NOT RUN** and **BLOCKED** are used whenever part of a criterion was not proven, and never count as PASS. At this revision AC-13 is PARTIAL (see its row), AC-09 is PARTIAL (best effort detection, independent confirmation still owed), AC-11 is `PENDING_HUMAN_RECEIPT`, and AC-06 is PASS only with the fixture-only limitation stated in its row. Everything marked PASS is the implementer's record after remediation of independent review rounds 1 to 7: the finding-by-finding record (what failed, the test that failed on the reviewed revision and passes now, the mutation control, and what was NOT fixed) is `docs/qa/review-round1-ledger.md`, and independent re-review of the final revision is still owed.

Test id format: `file :: describe > test title`. Stage A files are in `tests/unit/`; stage B files are named in the rows below and live in `tests/integration/` unless the row says `tests/unit/`; the acceptance suite is `tests/changeradar.spec.ts`; the end-to-end suites are `tests/e2e/smoke.spec.ts` (browser) and `tests/e2e/packaged.spec.ts`. Two files share the name `offline.test.ts`; rows give the directory for them. A title containing `%s`, `%i`, `%j` or a `${...}` placeholder is a parameterized test; every generated case ran.

## Not proven by these tests (stated, not hidden)

- **AC-11** needs a human receipt: `PENDING_HUMAN_RECEIPT`. The runbook harness and any automated run are supplemental only.
- **Live sandbox receipts: none.** No criterion depends on a live provider. Network contract checks were proven against local FIXTURE servers over real sockets; nothing is labelled live.
- **Independent code review and QA at the final revision** are not part of this record.
- **Browsers other than Chromium**, screen readers, forced-colors mode and touch input were not tested. The browser end-to-end run needs a Chromium build; the Node 22.12 container run skips it.
