# Writing a dependency manifest

ChangeRadar builds its dependency graph only from explicit, versioned JSON manifests that you write or export. It does not crawl your systems. This page is the operator-facing guide; the formal rules are in `docs/DOMAIN.md` and the machine-readable JSON Schema is `schemas/dependencies.json` (`schema_version` 1).

## What the MVP can and cannot tell you

- It answers: "which **declared** consumers can this proposed manifest change break, and through which path?"
- Contract checking is limited to a small required-field/type subset: for each `contract` node you list fields with a name, a type and whether the field is required. It compares those lists between a baseline and a proposal. It does **not** evaluate arbitrary JSON Schema, OpenAPI or protobuf compatibility, nested structure, enums, formats or value ranges.
- It never concludes that an undeclared dependency does not exist. A change with no declared consumer is reported as `NO_KNOWN_IMPACT` together with an explicit list of what was not known, not as "safe".
- Missing owners, stale or never-verified edges, placeholder nodes and undeclared contract fields on an affected path make the result `INCOMPLETE`. That is a request to fill in the manifest, not a pass.
- Manifests go stale. `verified_at` on each edge is how you say when a human or a check last confirmed it; edges older than the configured maximum age (default 30 days) count as stale.

## Minimal example

```json
{
  "schema_version": 1,
  "revision": "2026-09-29.1",
  "provenance": { "source": "billing-team-export" },
  "nodes": [
    { "id": "svc.billing", "kind": "service", "owner": "team-billing", "version": "3.2.0" },
    {
      "id": "contract.invoice",
      "kind": "contract",
      "owner": "team-billing",
      "version": "1.4.0",
      "contract": {
        "fields": [
          { "name": "invoice_id", "type": "string", "required": true },
          { "name": "amount", "type": "number", "required": true },
          { "name": "note", "type": "string", "required": false }
        ]
      }
    },
    { "id": "job.export", "kind": "job", "owner": "team-data", "version": "0.9.1" },
    { "id": "cred.warehouse", "kind": "credential_alias", "owner": "team-data", "version": "1" }
  ],
  "edges": [
    { "source_id": "svc.billing", "target_id": "contract.invoice", "relation": "produces",
      "source_file": "services/billing.yaml", "source_line": 4, "verified_at": "2026-09-28T09:00:00Z" },
    { "source_id": "job.export", "target_id": "contract.invoice", "relation": "consumes",
      "source_file": "jobs/export.yaml", "source_line": 12, "verified_at": "2026-09-28T09:00:00Z",
      "fields": ["invoice_id", "amount"] },
    { "source_id": "job.export", "target_id": "cred.warehouse", "relation": "requires",
      "source_file": "jobs/export.yaml", "source_line": 20, "verified_at": "2026-09-28T09:00:00Z" }
  ]
}
```

## Fields

- **nodes**: `id` (unique, letters, digits and `. _ : / @ -`), `kind` (`service`, `job`, `contract`, `credential_alias`, `artifact`), `version` (any text; `major.minor.patch` lets ChangeRadar tell breaking major bumps from compatible ones), `owner` (who to contact; leave it out only if you accept `INCOMPLETE` results that reach this node), optional `placeholder: true` for a node you know exists but have not described, optional `contract.fields` on contract nodes.
- **edges**: `source_id --relation--> target_id` where `relation` is `consumes`, `requires` or `produces`. `source_file` and `source_line` say where the dependency is declared, so every finding is traceable. `verified_at` is UTC (`...Z`). On an edge that consumes a contract, `fields` lists the contract fields that consumer actually uses; leave it out and ChangeRadar assumes the consumer depends on every **required** field.
- **credential aliases**: name the credential (`cred.warehouse`), never its value. A manifest containing something in a recognised secret shape is rejected in full and the error does not repeat the value. **This is best effort, not a guarantee**: detection is pattern based, so a secret in a shape that is not listed here passes. Recognised: private key blocks; cloud access keys (AWS); source host tokens (GitHub `ghp_`, `github_pat_`, GitLab `glpat-`); package and model registry tokens (npm `npm_`, Hugging Face `hf_`); chat and payment tokens (Slack `xox`, Slack and Discord webhook URLs, Stripe `sk_`/`rk_`/`whsec_`, `sk-` style API keys); SendGrid `SG.`, Twilio `SK`/`AC` identifiers, Google API keys and OAuth `ya29.` tokens, Azure `AccountKey=`/`SharedAccessKey=` connection strings; JWTs; `Bearer` and `Basic` credentials; `Cookie`, `Set-Cookie` and `Authorization` header values; passwords or tokens in URLs (`scheme://user:secret@host`, and a token-like name alone as in `https://tokenvalue@host`); and assignments such as `password = ...`, `"token": "..."`, `aws_secret_access_key = ...` (values that look random; a plain word such as `password=correcthorse` is redacted in logs but not rejected). Also recognised: PGP private key blocks (the armored header of a PGP private key block), `Cookie=`/`"Cookie": ` style keys, and quoted values that contain escaped quotes (the value is redacted through its real closing quote, including JSON inside JSON). A recognised shape is found whatever text sticks to its front (a letter, a digit, `_`, `%20`, a literal `\n` or `%0A` from an escaped header dump), with one deliberate exception: the two short prefixes `sk-` and `hf_` are not matched when a plain letter is glued to their front, because they occur inside ordinary words (`disk-`, `task-`, `risk-`, `pdf_`); after a digit, `_`, a space, a newline or an escaped newline they are matched. Round 3 also recognises a quoted credential KEY at any JSON depth (`{"a":{"b":{"password":"..."}}}` and the same inside escaped JSON strings), the bracket form `config[password]=...`, `name=password value=...` pairs, and (round 4) credential name/value pairs in either order, with other keys between the two halves, with a path-shaped or cookie name (`{"Name":"/prod/db/password","Type":"SecureString","Value":"..."}`, `{"value":"...","name":"session"}`), the `valueFrom` form of container environments, tuples and argument vectors (`["password","..."]`, `["run","--password","..."]`), in text at any JSON nesting depth and in objects (`redactDeep({name: "DB_PASSWORD", value})`), gaps of up to 64 characters between a key and its value, a quoted value with no closing quote (redacted to the end of the line or of the text), control characters inside a shape (folded away like zero-width characters), and credential words inside property names (`db_password`, `apiToken`, `client-secret`; identifier fields such as `credential_alias` stay readable). A cross-check after round 3 added: no fixed limit on the backslash run in front of a quoted key or value (JSON nested to any depth, tested to 13 layers), no limit on the text a credential word is glued to inside a key name (`aws_secret_access_key_for_the_production_environment=...`), a value on the line after `key:` (YAML, real or escaped line breaks, one list dash), the operators `=>` and `:=`, a bracketed token glued to a credential word (`pass<ghp_...>=value`), and a property name that itself holds a secret hides the value under it, so redacting twice gives the same result as redacting once. Matching sees through every default-ignorable character (zero width, joiners, bidi controls, fillers such as U+034F, U+115F, U+3164, U+FFA0), combining marks and fullwidth letters. Every other format character (general category Cf) is folded away as well, and every control character except tab, line feed and carriage return. One level of percent-encoding is decoded into a copy that is scanned too (`password%3D...`, `Authorization%3A%20Bearer%20...`, `https%3A%2F%2Fuser%3Apw%40host`); the spans map back onto the original text exactly, so only the secret's own characters are replaced. Redaction is repeated (at most 32 passes) until nothing changes, so redacting twice equals redacting once. A credential property name is recognised as a whole lower-cased key too (`PGPASSWORD`, `dbpass`, `signingkey`, `DATABASE_URL`, `cookies`, `Auth`), not only as separate words.

**Ordinary counters keep their number.** A view or export hides the value under any property name that contains `token` (and every other credential word). The one narrow exception is a short exact list of counters and limits (`tokens_used`, `tokens_total`, `tokens_remaining`, `token_count`, `token_limit`, `max_tokens`, `prompt_tokens`, `completion_tokens`, `total_tokens`, `tokenizer`): under one of those names a number or a boolean stays visible, while a string, an array, an object or null is still hidden. Every other name (`tokens`, `api_tokens`, `token`, `access_token`) is hidden whatever it holds.

**Also recognised (review round 5).** Name/value pairs written without JSON quoting, in either order and with other keys between the halves (`name=DB_PASSWORD value=...`, `name: password, value: ...`, a YAML list of `name:` and `value:` lines), and pairs whose value is a number, a bare word, an array or an object; pairs up to 600 characters apart with whole objects and arrays between them; the key spellings `name`/`key`/`header`/`k`/`id`/`label`/`field`/`variable`/`env`/`ParameterKey` for the name and `value`/`v`/`val`/`data`/`content`/`text`/`payload` (and any `...Value`) for the value; names that are paths, bracketed or braced (`/prod/db/password`, `password[0]`, `${DB_PASSWORD}`, up to 300 characters) and the name words connection string, `DATABASE_URL`, csrf, private, pin, pw, signature, sid, otp. In YAML: block scalars after a credential key (`password: |`, `>-`, `|2`, redacted to the end of the indented block), node properties (`&anchor`, `!!str`), a comment line after the key, flow sequences and mappings (`password: [a, S]`), nested list dashes. Also `PASSWORD ?= ...`, `+=`, `||=`, `??=`, `tool -p=...`, `ENV PASSWORD ...` and `ARG ...` lines, typed declarations (`password: string = "..."`), long flags whose last word is a secret word (`--db-password value`, `--api-key value`; not `--token-file`), Python string prefixes (`b'...'`, `r"..."`, `f"..."`), and the text keywords `session_id`, `sid`, `connection_string`, `DATABASE_URL`, `dsn`, `webhook`, `jwt`, `bearer`, `pw`, `pswd`, `pin`, `otp` and the signing, encryption, master and ssh key names, matching the property names hidden in objects. A bare `:` after `session_id`, `sid`, `connection_string`, `database_url`, `dsn`, `webhook_url`, `jwt`, `bearer`, `pw`, `pswd`, `pin`, `otp` and the signing, encryption, master, ssh, license, stripe, account and storage key names assigns only in the spaced style of YAML and config files (`dsn: value`, a blank, a quote or a line break after the colon); glued (`dsn:value`), joined by `.` or `-` to another word, or inside a route (`/sid:abc123`) it stays an identifier (`=` always assigns). A character that came from a `%XX` escape is data, never the end of a value (`password%3Dab%26cd...`), and an ordinary percent-encoded URL is unchanged. A property name is matched after the same fold as text (invisible, combining and fullwidth characters).

**Also recognised (review round 6).** The round-6 changes aimed at hiding no less than the tree they replaced, and the differentials that were run found no such text in the shapes they generate (the independent corpora of round 7 found a few garbled strings, listed below and pinned; this is a measured statement about generated corpora, not a guarantee about every text): a value that holds the name of the next credential (`pin: apikey :S`, `secret=abc%0Apassword="S"`, `sid=client_secret:="S"`, `otp":"null; <token": "S`) no longer takes that credential's secret with it, because the scan goes on inside a bare or quoted value (a short one always, a longer one while a budget of eight times the text lasts) and inside a block scalar; a value that starts with `#` (`password: #S`), with a bracket, brace or parenthesis group glued to more text (`password=[abc]S`, `password={}S`, `token:{a}S`, `password=(ab3)S`, closers glued behind the group as in `password={a}}S`: the group and the word that its closing character is glued to are the value; before round 7 only the square brackets were, and a random password that opened a brace or a parenthesis and closed it soon after was readable behind the closing character in every tree; a delimiter right behind the group ends the value like in any unquoted value, `password={ab},S`), or that looks like `key=` or `key:` (`DB_PASSWORD=Secret2024:`) is a value; a secret glued between a key word and its separator (`apikeyS:`) is hidden; a short anchor or tag followed by a backslash is part of the value; block scalar bodies that hold a quote or an apostrophe are read to their end at every JSON depth; a block scalar is read as the value of a name/value pair; name/value pairs are read to JSON depth 13 (tested; the bound is 2^19 characters between the halves, not 4,096); `credential: S`, pre-signed URL signatures (`?sig=`, `&sig=`, `X-Amz-Signature=`, `x-amz-security-token=`) are redacted. Frozen fixtures (`tests/fixtures/redaction-no-leak`, four files of 664 to 720 inputs, each hidden by the previous tree) and a differential over about nine million generated texts in three styles on more than thirty seeds found no text where a planted secret that the round-5 reviewed revision hid is now shown; against the round-6 reviewed revision the only such texts are the garbled class named below.

**Also recognised (review round 7).** A JSON escape of an ASCII character (Go and Gson write `=`, `'` and `"` as a backslash, `u`, `00` and two hex digits) and an HTML entity of one (`&quot;`, `&#34;`, `&#39;`, `&apos;`, `&amp;`, `&#61;`, `&#x3d;`) are decoded into the scanned copy like a `%XX` escape, so `password` followed by an escaped equals sign, HTML-quoted JSON and a key with one letter written as an escape are redacted; text of more than 512 K characters that holds any of these is refused whole, as for `%XX`. Pre-signed signatures in a query (`signature=`, `X-Goog-Signature=`, the CloudFront `Policy`, `Signature`, `Key-Pair-Id` set and the S3 `AWSAccessKeyId`, `Signature` pair). The plural credential names `passwords:`, `tokens:`, `secrets:` and `credentials:` as YAML parents of a list. `:=` (and `: =`) behind the names that assign with a spaced colon (`dsn := S`, `sid`, `jwt`, `bearer`, `pin`, `otp`, `session_id`, `webhook_url`, `pw`, `pswd`, `connection_string`, `database_url`). The user part of `https://TOKEN:x-oauth-basic@host`. The short keys `sid`, `pw`, `pswd`, `pin`, `otp`, long flags, `-p=`, `ENV` and `ARG` lines and bare name/value pairs are recognised after a line break written as text (a backslash and an n, r or t) as after a real one. `redactSecrets(redactSecrets(x))` equals `redactSecrets(x)` on every generated text of the differentials (0 of 200,000 in each of three styles at seed 9101; the round-6 build had 1 and 9), with one exception listed below. A word that starts with `!` is a YAML tag only when a blank, a line break or the end of the text follows it, so `password: !]*9H_`, `password: !'dx$awi` and `password: !{7eDk}` are values and are hidden (from the `!` to the furthest of the word, which runs to the next blank, comma, closing bracket or brace, backslash or quote, and the value read behind the `!`: a quoted value or a closed group, with the text glued to it); a verbatim tag `!<tag:yaml.org,2002:str>` is read to its closing angle bracket (at most 256 characters).

The tree before this one hid them only by swallowing the next key, which leaked other keys in more plausible input; the strings are pinned by tests named KNOWN LIMIT (`tests/unit/review-round6-known-limits.test.ts`; a fourth string of the first two rounds' soups, a `\ndsn:=` after a block scalar, is now hidden and is a control in `review-round7-shapes.test.ts`). **The class is wider than these strings, and it is described by counts, not by a promise.** In round 7 independent-style generators compared this tree with three older ones (a planted value that an older tree hid and this one shows is counted): over 1,520,000 generated texts per older tree (garbled soups, mutations of the frozen fixtures, key-dense strings, multi-line configuration documents with comments glued to keys) there were **2 against 435731e, 9 against the round-6 base and 12 against the round-7 base** in the runs of this tree, and the reviewers' own generators found more (the conformance, security and test reviews: at least 6 + 7 + 3 minimal strings against one tree or the other). Every one needs multi-layer percent-encoded or literal `\n` text, glued colons after a key that assigns only with a blank behind its colon, unbalanced quotes, keys inside comment words or block markers; no plausible plain variant that an older tree hid and this one shows was found (the plain variants that were tried leak, or are hidden, in every tree; this is a search result, not a proof). Twenty-three minimised strings (`tests/fixtures/redaction-no-leak/known-limit-garbled.json`) and five more from the security and test reviews (`tests/unit/review-round7-garbled-limits.test.ts`) are pinned as KNOWN LIMIT with the current output, in addition to the six of rounds 6 and 7 above; the total is at least 34, described here as "at least". Do not rely on this list as complete. The recognised shapes above are what is redacted; anything in this list is neither rejected nor redacted, and a plain-word credential (`password=correcthorse`) that the validator does not refuse is stored, and exported in a bundle's manifests, as written (views and reports redact it). Separately, in free text (a reason or an error detail) a bare `key:value` pair whose key looks like a credential word can be shown redacted even when it was an identifier such as `token:refresh`; that is accepted over the risk of leaving a secret. Do not rely on this as a control.

**Size cap, fail closed.** A string longer than 8 MiB, or longer than 512 K characters when it contains any non-ASCII character (folding allocates per character), is not scanned: the redactor replaces it by the fixed text `[REDACTED: value too large to scan]` and the manifest validator rejects it. That is a refusal, never a pass-through. Every string the server itself passes (bodies at most 64 KB, ids, revisions) is far below the cap. There are no scan windows: the whole string is scanned in one pass. Every scan also has a WORK BUDGET: the reads that could repeat for many starts (the run after `!` or `&`, an unquoted value, a `#` comment in a gap, the comment after a block header, a run of backslashes in the pair scan) are read once and counted, and a call that spends more than 64 counted steps per character (plus 65,536) is abandoned: the whole string is then replaced by the same fixed text as a string that is too large, never shown in part. Ordinary text costs about 1 to 5 steps per character, so a text that hits the budget is a hostile one; it is documented here so that a hidden-whole string is not mistaken for a defect.

**Identifiers are never rewritten.** Node ids, check keys, finding ids and the other identifier fields of a view or an export are redacted only at the strength the manifest validator applied when the id was imported, so an accepted id (for example `svc.token:refresh-service`) is shown and exported exactly as it was imported and two different ids never collapse into one. Free text (reasons, messages, descriptions) is redacted at log strength, and so is an `owner`: it is display text, not an identifier, so a hostile-looking owner such as `Authorization:abcdefgh` is shown as `Authorization:[REDACTED]` in views, while bundles and the manifest download keep it as written. Anything that leaves the server (reports, exports, node and edge views, snapshot summaries, bundles, logs) is redacted with the same patterns, so a shape that is not recognised there is not redacted either. The one exception is the stored manifest download (`GET /snapshots/{id}/manifest`, operator and admin): it is the hashed document itself and is returned as stored, because the import validator already refused secrets in it. The exception is a stored manifest that the CURRENT validator rejects (an earlier build accepted a value that the validator now refuses): it is served redacted, with the response header `x-changeradar-manifest-redacted` carrying the stored document's hash, and export and `verify-bundle` refuse that snapshot (`BUNDLE_SNAPSHOT_MISMATCH`, naming the snapshot id, the JSON locations and the rule, never the value).

## Limits and rejection

At most 10,000 nodes, 50,000 edges and 25 MB per manifest. These are checked before the manifest is processed. A manifest with duplicate node ids, an edge that points to an undeclared node, an unsupported `schema_version`, an unknown property or a malformed timestamp is rejected as a whole; nothing partial is kept.

Dependency cycles are allowed; they are reported and analysis terminates normally.
